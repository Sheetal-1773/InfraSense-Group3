- (decision) Architecture paradigm: Event-driven microservices with separate prediction engine service
- (decision) MVP Stack: React (frontend), FastAPI (backend), PostgreSQL (storage), OpenTelemetry Collector (telemetry), Prometheus Alertmanager (alerting)
- (decision) Enterprise Stack: Kubernetes deployment, Kafka for event streaming, InfluxDB/TimescaleDB for time-series, Grafana for visualization
- (decision) Core services: API Gateway, Telemetry Ingestion, Health Scoring Engine, Prediction Engine, Alert Service, Notification Service
- (decision) Data model: Components (servers, DBs, networks), Metrics (time-series), HealthScores, Predictions, Alerts, Recommendations
- (decision) Integrations: OpenTelemetry for telemetry ingestion, Prometheus remote-write, webhooks for PagerDuty/OpsGenie/ServiceNow
- (decision) AD-01: Prediction models use simple-first hierarchy (static → dynamic → trend → ML) with graceful degradation when confidence is low
- (decision) AD-02: All API communication uses JSON over HTTP/HTTPS; internal services may use gRPC for performance
- (decision) AD-03: Telemetry collectors deploy as sidecars or daemonsets with <2% CPU overhead requirement
- (decision) Deferred: Multi-cloud metric normalization approach (OQ-02 from PRD)

Original event-driven microservices target is deferred enterprise evolution, not the current spine.
- (decision) UPDATE: AD-01 amended in place — prediction hierarchy ratified as static thresholds -> dynamic (mean+2std) -> trend (linear regression); ML models NOT implemented (sklearn/pandas declared but unused) and deferred. Strategy confidence floors: static 70, dynamic 60, trend 50; below all floors stores 'Prediction unavailable — insufficient history' per FR-TTB-05.

- (decision) UPDATE: AD-03 amended — collection runs IN-PROCESS inside the monolith (async metric_collector loop, 10s interval); <2% CPU / <100MB RAM retained as the bound for any future out-of-process collector/agent deployment.
- (decision) UPDATE: AD-04 ratified — overlay intelligence implemented as a data-source adapter abstraction (LocalInfrastructureAdapter, InfrastructureSimulatorAdapter, MockSolarWindsAdapter) behind DataSourceManager; read-only from source systems; platform augments, does not replace, existing monitoring.
- (decision) UPDATE: AD-05 ratified — recommendation-only remediation enforced by remediation_guard (prevent_auto_remediation always blocks auto actions); recommended_action + runbook_url carried on Alert/Prediction, never executed.
- (decision) NEW AD-06: Data-source adapter abstraction — all component discovery and metric acquisition flows through DataSourceAdapter implementations registered in DataSourceManager; components tagged source/provider (local/simulated/solarwinds); downstream services (health, prediction, alerting) consume normalized data and must not know the source.
- (decision) NEW AD-07: Real-time push contract — background updater thread (5s default interval) is the single mutation driver: discovers components, updates metrics/health, checks alerts, runs prediction engine; pushes via WebSocket channels /ws/alerts, /ws/health, /ws/predictions (message types alert, health_update, prediction, metrics_update). Frontend subscribes per channel; no other write path.
- (decision) NEW AD-08: Alert classification & lifecycle — alerts typed reactive (post-breach) or predictive (pre-breach TTB); lifecycle open -> acknowledged -> resolved via POST /api/alerts/{id}/acknowledge and /resolve; dedup: one active/open alert per component+metric; classification and lifecycle are the single source of truth (reconciles the active/open vocabulary drift in the code).
- (decision) NEW AD-09: Deployment shape — modular monolith deployed as docker-compose: timescale/timescaledb pg16 (postgres), FastAPI backend (port 8000), Vite/React SPA (port 3000); demo apps customer/payment/auth-api (Flask, ports 4000-4002) as monitored targets. No Kubernetes/Kafka/cloud today; monolith decomposed by router+service boundaries so services can split out later without rework.
